# Push decode from 1.18 to 20+ tok/s

## The problem, stated exactly

Decode runs at **1.18 tok/s**, about **850 ms per token**. The target is 20+.

Measured breakdown of one decode step (`KAPLUMBA_PROFILE_PHASES=1`):

```
embed   0.17 ms
layers 783 ms      cpu_encode 0.00 ms, gpu_wait 783 ms
head    9.3 ms
total  793 ms
```

The linear matvecs — the thing I spent the most time on — are now only about
**220 ms** of that. They were made **1.9–2.3× faster** and verified. **Roughly
560 ms per token is two kernels that serialise to a single thread whenever
`rows == 1`, which is exactly the shape of a decode step.**

There are two roofs, and they are not the same:

| Roof | tok/s | Basis |
|---|---:|---|
| Bandwidth | 22.6 | 273 GB/s ÷ 12.06 GB/token |
| ALU, measured | higher than 18.8 | see below |

Measured per-op-class peak on this machine (`examples/alu_peak.rs`, four
independent accumulator chains so the loop is issue-bound, not latency-bound):

| Workload | Measured |
|---|---:|
| shift / and / xor | 2.85e12 ops/s |
| multiply + add | 2.90e12 ops/s |
| fp16 packed as `half2` | **5.10e12 ops/s** |
| fp32 FMA (calibration) | 4.35e12 ops/s |

The FMA figure matches Apple's published M4 Pro shader throughput, so the
harness is calibrated. **Multiply is full rate**, and **fp16 doubles when packed
as `half2`**. An earlier version of this analysis guessed a 2.4 GHz clock and
concluded 19 tok/s was the ALU wall; that guess was wrong in the machine's
favour, and the corrected conclusion is that ALU headroom is larger than
bandwidth headroom. The binding roof is bandwidth at 22.6 tok/s, and 20 is
therefore *arithmetically* reachable — it is an efficiency problem, not a
physical one.

## Why it is slow, part by part

### 1. `rms_norm` runs on one thread (measured, ~143 ms/token)

`crates/kernels/src/elements.metal:92`:

```metal
if (gid >= params.rows) return;                  // one thread per ROW
for (uint i = 0; i < count; ++i) sum += v * v;   // serial over 5376
for (uint i = 0; i < count; ++i) out[i] = ...;    // serial again
```

`encode_rms_norm` dispatches `rows` threads. A decode step has `rows == 1`, so a
**single GPU thread** walks 5376 elements twice, serially, in fp32.

Measured against its own siblings at the same shapes (`examples/elem_bench.rs`):

| Op | µs |
|---|---:|
| **`rms_norm` 1×5376** | **595.7** |
| `gated_gelu` 21504 | 3.0 |
| `rope` 8×512 | 3.2 |
| `copy_last_row` 1×5376 | 2.7 |
| `residual_add` 1×5376 | 2.3 |

200× slower than a 4× *larger* op beside it (`gated_gelu` at 21504 elements vs
`rms_norm` at 5376).

Per layer, there are **7 norms** total, but only **4 run on a single thread at
decode** (width=5376, rows=1): `input_norm`, `post_attention_norm`,
`pre_ffn_norm`, `post_ffn_norm`. The other 3 are q/k/v norms over head
dimensions with multiple rows (q_norm: 32 rows, k_norm: 16 or 4 rows, v_norm:
16 or 4 rows), so they dispatch multiple threads already.

The single-threaded norms: 4 per layer × 60 layers + 1 final norm = **241
dispatches** per token ≈ **143 ms** at 596 µs each.

`rms_norm_unweighted` is used for v_norm (not `pre_ffn_norm`); `pre_ffn_norm`
uses the weighted variant.

### 2. `online_attention` runs on 32 threads (inferred, the rest of ~380 ms)

`crates/kernels/src/attention.metal:14`:

```metal
if (gid >= params.queries * params.q_heads) return;   // 1 * 32 = 32 threads
float accum[512];                                      // 2 KB of registers each
```

The model has **32 query heads** (not 8 — the 4/16 figures are *KV* heads, with
GQA grouping 8/2 queries per KV head respectively). Decode therefore runs
attention on **32 threads**, each holding a 512-float accumulator and scanning
every key serially. Sliding layers (50 of 60) scan their whole 1024-slot ring
with `head_dim=256`. Full-attention layers (10 of 60) scan all cached keys with
`head_dim=512`. The 2 KB register array per thread (64 KB across 32 threads)
caps occupancy at one or two threadgroups per core.

This is the largest remaining slice and is **not yet timed** — see Q3.

### 3. The matvec is now 1.9–2.3× faster but loads still dominate it

`crates/kernels/src/linear.metal`, `linear_gemv_exl3_k*`, generated by
`scripts/gen_exl3_gemv.py`:

| Shape | Before | After |
|---|---:|---:|
| `q_proj` 5376×5376 | 21.1 GB/s | 40.2 GB/s |
| `up_proj` 5376×21504 | 40.8 | 55.6 |
| `down` 21504×5376 | 23.0 | 52.9 |
| `lm_head` 5376×262144 | 53.3 | 63.8 |

Phase split inside the kernel (`q_proj`): **loads 0.336 ms of 0.612 ms (55%),
shifts 0.244 ms (40%), codebook 0.032 ms (5%)**. The overlapping 16-bit window
means each ring word is touched by several lanes at varying unaligned offsets,
so reads do not coalesce. The `ALIGNED` specialisation (one 32-bit load instead
of two 16-bit) already recovered half of that cost.

### 4. The codebook is a hash where a table would do

MCG decode is ~4 int ops per weight: `x = s * 0xCBAC1FED; x = (x & mask) ^ k;
half low + half high`. But at 3 bpw only the **top `ka` bits of a 16-bit code
carry information**, so the codebook is a function of `2^ka` inputs — 8 values
at the model's rate. A 256-entry table covers every integer rate 1..8. That
deletes the multiply, the mask, the xor and the shift, and leaves a lookup.

This is the single change that could take the matvec past its current wall, and
it is **measured as unproven** — the A/B harness hung (see Q1).

## How to get to 20 tok/s

Budget arithmetic. One token streams 12.06 GB and decodes 32.2e9 weights.

| Stage | Change | Token cost | tok/s |
|---|---|---:|---:|
| now | — | 850 ms | 1.18 |
| 1 | parallel `rms_norm` | 850 → 710 ms | 1.4 |
| 2 | split-K `online_attention` | 710 → 330 ms | 3.0 |
| 3 | matvec to ~100 GB/s (cooperative ring load) | 330 → 240 ms | 4.2 |
| 4 | `half2` codebook packing | 240 → 170 ms | 5.9 |
| 5 | codebook LUT | 170 → 130 ms | 7.7 |
| 6 | remaining matvec efficiency | 130 → 50 ms | **20** |

Stage 1 saves ~143 ms (the single-threaded norm cost). Stage 2 is estimated
from the ~380 ms attention residual. These figures need revision once Q3 is
answered with real measurements; the budget table is arithmetic on a mix of
measured and inferred costs.

Stage 6 needs 12.06 GB at 240 GB/s, which is 88% of peak bandwidth. That is
aggressive; stages 1–5 are ordinary work and already buy ~7×.

**Order matters.** Stages 1 and 2 are certain, uncontroversial parallelism bugs
and are worth ~3× on their own. Do them before anything else.

## Requirements

- **R1** `rms_norm_weighted` and `rms_norm_unweighted` reduce in parallel: one
  **threadgroup** (256 threads) per row, strided partial sums, barrier tree
  reduction. Dispatched only when `rows` is small, so prefill is untouched.
- **R2** `online_attention` parallelises over keys for decode via two-pass
  flash-decoding: per-split `(max, l, acc)`, then a combine pass with
  `exp(m_i - m_global)` rescaling. No fp32 atomics.
- **R3** The per-thread `float accum[512]` is removed for small grids, staged in
  threadgroup memory instead, so occupancy is not capped at 1–2 groups/core.
- **R4** The codebook is a table. Entries built once per threadgroup from the
  existing hash, indexed by `code >> (16 - ka)`. Must reproduce the hash
  bit-for-bit for all rates and codebooks.
- **R5** `half2` packing where two codes are available in adjacent lanes, giving
  two fp16 codes per lane at 5.10e12 ops/s instead of one at half that.
- **R6** The matvec's ring load is made cooperative: the 32 lanes of a simdgroup
  collectively need one `256 * ka`-bit ring, so load it once (ideally one 128-bit
  load per thread) into registers or threadgroup memory instead of three
  overlapping 32-bit loads per lane. Cuts global load instructions ~4×.
- **R7** Every kernel on the decode path gets a microsecond cost measurement in
  `elem_bench`, so a future serialisation is caught in seconds, not hours.
- **R8** Output must match within float tolerance. No `output_identity` test
  exists yet; one must be created (a generation comparison against a recorded
  baseline at temperature 0).
- **R9** Prefill must not regress (8.4 tok/s at 134 tokens today).

## Acceptance criteria

1. `rms_norm 1×5376` under 20 µs (from 595.7).
2. `online_attention` at `queries=1, keys=200, 32 q-heads, 16 kv-heads,
   dim=256` (sliding shape) and `queries=1, keys=200, 32 q-heads, 4 kv-heads,
   dim=512` (full shape) under 200 µs, scaling sub-linearly in key count.
3. `q_proj` matvec at or above 100 GB/s (from 40.2).
4. Decode **≥ 5 tok/s** after R1+R2 alone; **≥ 11 tok/s** after R4+R5; 20 is the
   target, not the gate.
5. Full suite green; prefill ≥ 8 tok/s; output comparison within tolerance.

### Q1. Does the codebook lookup table actually beat the hash?

The single most promising idea in this spec and the least proven. At 3 bpw only
the top `ka` bits of a 16-bit code carry information, so the codebook is a
function of `2^ka` inputs — 8 values at this model's rate, 256 covering every
integer rate 1..8. Replacing `mul / and / xor / shift` with a lookup should
delete the dominant per-weight cost.

The catch: Metal `thread` arrays can spill to local memory, and a spilled lookup
is worse than the hash it replaces. The A/B harness (`examples/cb_bench.rs`)
hung before producing a number — most likely the CPU-side fill of a 1 GB buffer,
the same failure mode as the streaming probe that had to be deleted.

**Decision it drives:** if a table pays, stage 5 is real and 11 tok/s is on the
table. If it spills, the fallback is a `constant`-address-space table in a small
buffer; if that also fails, drop the idea and record why rather than iterating.

### Q2. Is 20 tok/s reachable at all?

Stage 6 needs 12.06 GB at 240 GB/s, which is 88% of peak. No kernel I have
measured gets close to that: the best projection is `lm_head` at 63.8 GB/s, 23%
of peak. ishizuki reports ~11 tok/s on M4 Pro and ~20 on M1 Max (400 GB/s),
which is consistent with a practical ceiling well under the naive roofline on
both.

**Decision it drives:** T18 exists solely to let this spec finish with "11 tok/s
is the machine" as a legitimate, recorded result. Stages 1–5 are ordinary work
and already buy ~7×; stage 6 is the only part that may not be reachable, and it
should not be allowed to hold the rest hostage.

### Q3. How much of the ~380 ms is attention?

`online_attention` is inferred to be the second-largest cost from its structure
— `queries * q_heads` threads with a `float[512]` accumulator each, so 32
threads at decode — but it has never been timed. The 143 ms of norms is
measured; the attention figure is arithmetic on a guess.

**Decision it drives:** the size of stage 2, and whether split-K attention plus
dropping `accum[512]` is one stage or two. If attention is much smaller than
380 ms, the budget needs re-deriving and something else is missing.

### Q7. Would a repacked trellis beat any kernel work?

The structural cost is that the 8 lanes of a simdgroup read overlapping windows
of one `256 * ka`-bit ring at varying unaligned offsets, so reads do not
coalesce — 55% of matvec time is loads. A layout where a simdgroup reads
contiguous bytes would remove that entirely.

It requires rewriting the checkpoint at load time, so it is a large change, and
it is also the only route I can see past roughly 11 tok/s. Deliberately deferred
until there is evidence it is needed.

**Decision it drives:** whether stage 6 is a tuning effort or a format change.

### Q5. Can `half2` accumulation replace fp32 in the matvec?

Measured `half2` is 5.10e12 ops/s against 4.35e12 for fp32 FMA, and a `half2`
accumulate handles two partial sums in one op. Over a 5376-element dot product
that risks precision, and the spec forbids quality loss, so this is
measurement-gated rather than assumed.

**Decision it drives:** whether stage 4 is worth doing at all.

### Q6. What bandwidth do *mapped* weights actually stream at?

Every GEMV number in this spec comes from an arena-resident buffer. The
offloaded `embed_tokens` and `lm_head` are file-backed and page-cache-served.
If those stream slower than arena memory, the effective roof is below 22.6 and
every projection in the budget table is optimistic.

**Decision it drives:** whether the offload that bought 15.12 → 11.51 GiB is
costing throughput, which would be a genuine trade-off to surface rather than
discover later.

### Q4. Does the sliding-window ring need a maintained bound?

Sliding layers scan all 1024 slots every step regardless of how few are live. A
running position bound, or a compacted ring, could cut that — but it changes
cache semantics and must not break the ring buffer.

**Decision it drives:** a possible extra stage after T10, only if attention
profiling shows the sliding scan dominating.

### Q8. Is `queries`-batching being left on the table?

Answered: no. `exl3_matvec` supports up to 8 rows per pass, reusing decoded
weights across queries, but decode has exactly one query. This only helps
speculative decoding, which is out of scope by standing restriction.

## Risks

- **Two code paths per kernel** doubles the test matrix. Test both explicitly at
  `rows = 1` and `rows = 64`.
- **A tree reduction reorders the sum**, so logits shift in the last bits.
  The output test will need a tolerance form. Expected, not a regression.
- **Register pressure** in the attention combine pass: `head_dim` floats per
  partial per thread. May need chunking.
- **Prefill regressions** are the most likely silent damage, since these kernels
  are shared. Gate every change on the prefill measurement in R9.
