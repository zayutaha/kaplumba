# Push decode from 1.18 to 20+ tok/s

## The problem, stated exactly

Decode runs at **1.18 tok/s**, about **850 ms per token**. The target is 20+.

Measured breakdown of one decode step (`KAPLUMBA_PROFILE_PHASES=1`):

```
embed   0.17 ms
layers 783 ms      cpu_encode 0.00 ms, gpu_wait 783 ms
head    9.3 ms
total  793 ms
```

The linear matvecs — the thing I spent the most time on — are now only about
**220 ms** of that. They were made **1.9–2.3× faster** and verified. **Roughly
560 ms per token is two kernels that serialise to a single thread whenever
`rows == 1`, which is exactly the shape of a decode step.**

There are two roofs, and they are not the same:

| Roof | tok/s | Basis |
|---|---:|---|
| Bandwidth | 22.6 | 273 GB/s ÷ 12.06 GB/token |
| ALU, measured | higher than 18.8 | see below |

Measured per-op-class peak on this machine (`examples/alu_peak.rs`, four
independent accumulator chains so the loop is issue-bound, not latency-bound):

| Workload | Measured |
|---|---:|
| shift / and / xor | 2.85e12 ops/s |
| multiply + add | 2.90e12 ops/s |
| fp16 packed as `half2` | **5.10e12 ops/s** |
| fp32 FMA (calibration) | 4.35e12 ops/s |

The FMA figure matches Apple's published M4 Pro shader throughput, so the
harness is calibrated. **Multiply is full rate**, and **fp16 doubles when packed
as `half2`**. An earlier version of this analysis guessed a 2.4 GHz clock and
concluded 19 tok/s was the ALU wall; that guess was wrong in the machine's
favour, and the corrected conclusion is that ALU headroom is larger than
bandwidth headroom. The binding roof is bandwidth at 22.6 tok/s, and 20 is
therefore *arithmetically* reachable — it is an efficiency problem, not a
physical one.

## Why it is slow, part by part

### 1. `rms_norm` runs on one thread (measured, ~179 ms/token)

`crates/kernels/src/elements.metal:92`:

```metal
if (gid >= params.rows) return;                  // one thread per ROW
for (uint i = 0; i < count; ++i) sum += v * v;   // serial over 5376
for (uint i = 0; i < count; ++i) out[i] = ...;    // serial again
```

`encode_rms_norm` dispatches `rows` threads. A decode step has `rows == 1`, so a
**single GPU thread** walks 5376 elements twice, serially, in fp32.

Measured against its own siblings at the same shapes (`examples/elem_bench.rs`):

| Op | µs |
|---|---:|
| **`rms_norm` 1×5376** | **595.7** |
| `gated_gelu` 21504 | 3.0 |
| `rope` 8×512 | 3.2 |
| `copy_last_row` 1×5376 | 2.7 |
| `residual_add` 1×5376 | 2.3 |

200× slower than a 9× *larger* op beside it. Five norms per layer across 60
layers plus the final norm: **301 per token ≈ 179 ms.**

`rms_norm_unweighted` (`pre_ffn_norm`) has the identical structure.

### 2. `online_attention` runs on 8 threads (inferred, the rest of ~380 ms)

`crates/kernels/src/attention.metal:14`:

```metal
if (gid >= params.queries * params.q_heads) return;   // 1 * 8 = 8 threads
float accum[512];                                      // 2 KB of registers each
```

Decode therefore runs attention on **8 threads**, each holding a 512-float
accumulator and scanning every key serially, twice. Sliding layers scan their
whole 1024-slot ring. The 2 KB register array also caps occupancy at one or two
threadgroups per core. This is the largest remaining slice and is **not yet
timed** — see Q3.

### 3. The matvec is now 1.9–2.3× faster but loads still dominate it

`crates/kernels/src/linear.metal`, `linear_gemv_exl3_k*`, generated by
`scripts/gen_exl3_gemv.py`:

| Shape | Before | After |
|---|---:|---:|
| `q_proj` 5376×5376 | 21.1 GB/s | 40.2 GB/s |
| `up_proj` 5376×21504 | 40.8 | 55.6 |
| `down` 21504×5376 | 23.0 | 52.9 |
| `lm_head` 5376×262144 | 53.3 | 63.8 |

Phase split inside the kernel (`q_proj`): **loads 0.336 ms of 0.612 ms (55%),
shifts 0.244 ms (40%), codebook 0.032 ms (5%)**. The overlapping 16-bit window
means each ring word is touched by several lanes at varying unaligned offsets,
so reads do not coalesce. The `ALIGNED` specialisation (one 32-bit load instead
of two 16-bit) already recovered half of that cost.

### 4. The codebook is a hash where a table would do

MCG decode is ~4 int ops per weight: `x = s * 0xCBAC1FED; x = (x & mask) ^ k;
half low + half high`. But at 3 bpw only the **top `ka` bits of a 16-bit code
carry information**, so the codebook is a function of `2^ka` inputs — 8 values
at the model's rate. A 256-entry table covers every integer rate 1..8. That
deletes the multiply, the mask, the xor and the shift, and leaves a lookup.

This is the single change that could take the matvec past its current wall, and
it is **measured as unproven** — the A/B harness hung (see Q1).

## How to get to 20 tok/s

Budget arithmetic. One token streams 12.06 GB and decodes 32.2e9 weights.

| Stage | Change | Token cost | tok/s |
|---|---|---:|---:|
| now | — | 850 ms | 1.18 |
| 1 | parallel `rms_norm` | 850 → 670 ms | 1.5 |
| 2 | split-K `online_attention` | 670 → 290 ms | 3.4 |
| 3 | matvec to ~100 GB/s (cooperative ring load) | 290 → 200 ms | 5.0 |
| 4 | `half2` codebook packing | 200 → 130 ms | 7.7 |
| 5 | codebook LUT | 130 → 90 ms | 11 |
| 6 | remaining matvec efficiency | 90 → 50 ms | **20** |

Stage 6 needs 12.06 GB at 240 GB/s, which is 88% of peak bandwidth. That is
aggressive; stages 1–5 are ordinary work and already buy 9×.

**Order matters.** Stages 1 and 2 are certain, uncontroversial parallelism bugs
and are worth 4.4× on their own. Do them before anything else.

## Requirements

- **R1** `rms_norm_weighted` and `rms_norm_unweighted` reduce in parallel: one
  **threadgroup** (256 threads) per row, strided partial sums, barrier tree
  reduction. Dispatched only when `rows` is small, so prefill is untouched.
- **R2** `online_attention` parallelises over keys for decode via two-pass
  flash-decoding: per-split `(max, l, acc)`, then a combine pass with
  `exp(m_i - m_global)` rescaling. No fp32 atomics.
- **R3** The per-thread `float accum[512]` is removed for small grids, staged in
  threadgroup memory instead, so occupancy is not capped at 1–2 groups/core.
- **R4** The codebook is a table. Entries built once per threadgroup from the
  existing hash, indexed by `code >> (16 - ka)`. Must reproduce the hash
  bit-for-bit for all rates and codebooks.
- **R5** `half2` packing where two codes are available in adjacent lanes, giving
  two fp16 codes per lane at 5.10e12 ops/s instead of one at half that.
- **R6** The matvec's ring load is made cooperative: the 32 lanes of a simdgroup
  collectively need one `256 * ka`-bit ring, so load it once (ideally one 128-bit
  load per thread) into registers or threadgroup memory instead of three
  overlapping 32-bit loads per lane. Cuts global load instructions ~4×.
- **R7** Every kernel on the decode path gets a microsecond cost measurement in
  `elem_bench`, so a future serialisation is caught in seconds, not hours.
- **R8** Output must match within float tolerance; `output_identity` guards it.
- **R9** Prefill must not regress (8.4 tok/s at 134 tokens today).

## Acceptance criteria

1. `rms_norm 1×5376` under 20 µs (from 595.7).
2. `online_attention` at `queries=1, keys=200, 8 q-heads, 4 kv-heads, dim=512`
   under 200 µs, scaling sub-linearly in key count.
3. `q_proj` matvec at or above 100 GB/s (from 40.2).
4. Decode **≥ 5 tok/s** after R1+R2 alone; **≥ 11 tok/s** after R4+R5; 20 is the
   target, not the gate.
5. Full suite green; prefill ≥ 8 tok/s; `output_identity` within tolerance.

## Open questions

These are the things I do not know, and several of them change the plan.

- **Q1. Does the codebook LUT actually pay?** The A/B harness hung before
  producing a number. A LUT replaces 4 int ops with one lookup, but Metal
  `thread` arrays may spill to local memory, and a spilled lookup is worse than
  the hash. **Must be measured before R4 is attempted.** If the table spills,
  the alternative is a `constant`-address-space table in a small buffer, or
  exploiting that the 8 codes of a lane can be decoded with shared subexpressions.
- **Q2. Is 20 tok/s reachable at all, or is stage 6 fantasy?** 88% of peak
  bandwidth is required. ishizuki reports ~11 tok/s on M4 Pro and ~20 on M1 Max
  (400 GB/s), which suggests 88% is not attained in practice. **If Q1 fails and
  stages 3–5 land short, the honest destination is 11–13 tok/s and we should say
  so rather than chase 20.**
- **Q3. How much of the ~380 ms is attention?** Inferred from the kernel's
  structure, never timed. Add it to `elem_bench` first; it sizes stage 2.
- **Q4. Does the sliding-window ring need a maintained bound?** Sliding layers
  scan all 1024 slots every step. A running min/max position, or a compacted
  ring, could cut that, but it changes cache semantics and must not break the
  ring buffer.
- **Q5. Can fp16 accumulation replace fp32 in the matvec?** The 5.10e12 `half2`
  rate is nearly 2× the 4.35e12 fp32 FMA rate, and `half2` accumulation is one
  op for two partial sums. Risks precision over a 5376-element dot product;
  needs a tolerance test, and the spec forbids quality loss, so this is
  measurement-gated.
- **Q6. How much of the practical bandwidth is reachable for *mapped* weights?**
  Every GEMV bench number is from an arena-resident buffer. The offloaded
  `embed_tokens` and `lm_head` are file-backed; if those stream slower, the
  effective roof drops below 22.6.
- **Q7. Would a repacked trellis layout help more than any kernel work?** The
  fundamental cost is that 8 lanes read overlapping windows of a 96-byte ring.
  A layout where a simdgroup reads contiguous bytes would remove the
  non-coalescing entirely. It requires rewriting the checkpoint at load time, so
  it is a big change — but it may be the only route past ~11 tok/s. Worth a
  design note before committing to stage 6.
- **Q8. Is `queries`-batching worth it?** `exl3_matvec` supports up to 8 rows per
  pass, reusing the decoded weight for several queries. Decode has one query, so
  this only helps speculative decoding, which is out of scope. Confirm it is not
  being left on the table for some other reason.

## Risks

- **Two code paths per kernel** doubles the test matrix. Test both explicitly at
  `rows = 1` and `rows = 64`.
- **A tree reduction reorders the sum**, so logits shift in the last bits.
  `output_identity` will need a tolerance form. Expected, not a regression.
- **Register pressure** in the attention combine pass: `head_dim` floats per
  partial per thread. May need chunking.
- **Prefill regressions** are the most likely silent damage, since these kernels
  are shared. Gate every change on the prefill measurement in R9.
